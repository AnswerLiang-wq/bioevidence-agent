# BioEvidence Agent v0.4：AI 产品经理作品集案例

## 一句话结论

我把一个偏工程验证的生物医学检索 Agent 产品化为可本地运行、可筛选、可导出的 PubMed 证据包 Demo；在一次真实形成性试点中发现测量与证据范围问题后，没有继续堆参与者或包装成功数据，而是停止扩样、冻结失败记录，并把高风险场景转成 8 个可复现的合成回归控制。

项目证明的是产品定义、工程落地、评测诊断和诚实决策能力；它没有证明用户效率提升、临床可靠性或开放世界泛化。

## 1. 背景与产品问题

生命科学研究者核验一个具体主张时，通常需要组合搜索式、打开多篇 PubMed 记录、判断研究是否真正回答问题，并复制 PMID、片段和笔记。普通对话式模型可以给出流畅结论，但不一定保留“哪句话来自哪篇摘要、原始字节是否变化、证据是否错了人群或终点”的完整链路。

因此，我把问题定义为：

> 帮助能够自行做科学判断的研究者更快组织一小组可检查的 PubMed 证据，而不是替研究者给出治疗或科学结论。

目标用户是经常检索文献的生命科学研究生和初级研究者。患者、个人医疗建议、系统综述、全文证据和敏感研究内容不在首版范围内。

## 2. 为什么不做“回答所有生物医学问题”

开放式问答同时要求开放世界召回、论文身份识别、终点解释、效应量理解、证据分层和临床边界控制。任一环节失败都可能被最终流畅答案掩盖。

首版因此收窄为一个可验证工作流：输入一个具体研究主张，返回少量候选 PubMed 卡片，由人判断接受、排除和方向，最后导出带来源链的证据包。系统把“检索到论文”和“论文足以回答问题”明确分开。

## 3. MVP 与边界

MVP 提供：

- Standard 固定候选与 Live PubMed 发现两种明确标记的模式；
- 每次展示 3–5 张证据卡；
- PMID、DOI、PubMed 链接、题名、年份和 publication type；
- 摘要精确片段、字符偏移、记录 Hash 和片段 Hash；
- 接受、排除、笔记和人工方向选择；
- JSON 与 Markdown 证据包导出；
- 本地、最小化且不保存问题和笔记正文的事件记录；
- 无结果、无摘要、外部服务失败、超时和医疗建议等明确状态。

Product Demo 的运行时是 PubMed 检索加本地 BM25 排序。多语言 E5、RRF 和 cross-encoder reranker 属于独立的 Agent Engineering 评测链路，不能把后者的指标写成 Web Demo 的实际运行效果。

## 4. 技术与评测设计

### Agent Engineering 层

- PubMed E-utilities 检索与抓取；
- BM25、多语言 E5、RRF 与 cross-encoder reranker；
- typed `search/fetch/resolve/inspect` 工具；
- exact-span、PMID/DOI、来源 URL 与 SHA-256 溯源；
- 冻结数据、模型版本、报告、依赖锁、CI 和 release manifest。

### Product Demo 层

- Python 标准库本地 HTTP 服务，绑定 `127.0.0.1`；
- 静态 HTML/CSS/JavaScript，无账户和云端存储；
- 服务端持有检索结果，拒绝伪造 card ID；
- 结构化导出和隐私最小化事件日志；
- 对外部 PubMed 失败采用显式降级，不伪造结果。

## 5. 核心实验与真实结果

| 实验 | 样本与结果 | 能说明什么 | 不能说明什么 |
|---|---|---|---|
| Title-assisted 公开闭集 | 500 题；答案 accuracy 0.558，macro-F1 0.383 | 冻结闭集中的答案基线 | 开放世界泛化或临床可靠性 |
| Abstract-only 压力测试 | 500 题；reranked Recall@10 0.990、MRR 0.982、nDCG@10 0.984；12 次 rank drop、5 次 top-10 miss | 去掉标题泄漏后检索仍强，但不是完美 | 新疾病、新论文或真实查询分布召回率 |
| Evidence-utilization 负对照 | 500 个 non-test OOF 样例；正确上下文 0.536、打乱上下文 0.486，差 +5.0 个百分点，McNemar `p=0.066` | 结果与匹配上下文存在方向一致的敏感性 | 可靠推理或统计显著提升 |
| v0.4 软件审计 | 完整本地运行 46/46 测试通过；Ruff 通过 | 已验证全部软件合同，包括本地端口绑定 | 用户成功率和生产可用性 |
| 合成 scope controls | 8/8 pass | 声明元数据上的 fail-closed 策略确定可复现 | 自动读懂论文或科学判断正确 |
| 形成性试点 | 1 人、2 条尝试任务、0 条可评估、0 个 VEPS 观测 | 暴露流程与测量风险 | 用户价值、节时、信任或复用意愿 |

冻结工程实验均使用本地 CPU，模型/API 费用为 USD 0.00。Title-assisted 端到端延迟中位数为 1.109 秒、p95 为 1.235 秒，但这不代表 Live PubMed 或完整用户任务的延迟。

## 6. 形成性试点：我没有把失败修成成功

原计划使用 VEPS（Verified Evidence Pack Success）衡量是否在 12 分钟内导出足够、可访问、片段一致且不过度结论化的证据包。一次真实匿名试点实际执行了 2 条任务，但审计发现：

- 手工计时字段与 UTC 时间戳冲突；
- Standard 任务中发生模式切换，导出属于 Live 路径；
- `timeout` 和 source-open 记录在工作簿、笔记与事件流间不一致；
- 空白/评分单元格存在无效占位值；
- Agent 导出的 PMID 都是真实来源，但 3 条中有 2 条与决定性干预或终点不匹配；
- 手工结果没有保留可复核的原文精确片段与 Hash。

因此两条任务均按规则标记为 `not_evaluable`。这里的正确表述是“0 个 VEPS 观测”，而不是“VEPS 为 0%”，因为分母中没有可评估任务。

试点原始材料被保留在 Git 忽略的私有目录；没有录音、没有隐私事件，公开仓库不含逐条参与者材料。

## 7. 关键 PM 决策：为什么停止扩样

继续招募并不能修复已经发生的数据冲突。若指标生成、模式约束和证据范围仍不可靠，更多参与者只会提高记录数量，不会提高结论有效性。

我在“继续追求漂亮的人数”和“承认当前问题不可回答”之间选择后者：

1. 冻结本次试点为形成性失败，不覆盖原记录；
2. 取消后续真人研究，不报告节时、成功率、信任或复用数据；
3. 把资源转向可验证的风险控制、文档一致性和可复现发布；
4. 将项目停止条件限定为一个合格作品集，而不是继续扩展成临床级评测计划。

这是资源约束下的范围管理，不是宣称产品验证成功，也不是宣称用户不需要产品。用户价值仍然未知。

## 8. 从失败中产生的 8 个合成控制

为了不让试点只留下文字复盘，我把高风险证据范围问题变成 8 个冻结的合成用例：

1. 同物种、同人群、同干预、同终点、同时间的 direct match，可进入决定性人工复核候选；
2. population mismatch，fail closed；
3. species mismatch，fail closed；
4. intervention mismatch，fail closed；
5. endpoint mismatch，fail closed；
6. timepoint mismatch，fail closed；
7. `context_only` 不得成为决定性候选；
8. 任一 scope 为 `unknown` 时不得成为决定性候选。

所有结果都保留 `requires_human_review=true`，并明确
`scientific_judgment=not_performed`。实现比较的是预先声明的规范化元数据，不从自然语言自动抽取 PICO，也不输出 supported/contradicted 或置信度。

## 9. 我作为 AI 产品经理完成了什么

- 将开放式“医学问答”收敛为单一、可演示、有人类最终判断的证据包工作流；
- 区分用户价值指标、工程 benchmark 和软件合同测试；
- 识别并量化标题泄漏，设计 abstract-only 压力测试；
- 用 shuffled-context 负对照检查模型是否真正利用证据；
- 设计来源溯源、失败状态、隐私最小化和医疗边界；
- 从一次失败试点中识别 measurement integrity 与 evidence scope 风险；
- 主动停止无效扩样，把洞察转成自动化回归控制；
- 形成可本地运行、可复现测试、可审计发布的 GitHub 作品集。

## 10. 最终可说与不可说

可以说：

- 构建了 BM25 + E5 + RRF + reranker 的可审计生物医学证据 Agent；
- 在 500 条公开 PubMedQA 上完成冻结评测、去标题压力测试和负对照；
- 将能力产品化为本地证据卡筛选与导出 Demo；
- 一次形成性试点发现了不可评估的数据和证据范围问题，并转成 8 个合成控制；
- 因证据不足主动停止真人扩样并限制结论。

不能说：

- 证明用户更快、更信任或愿意复用；
- VEPS 为 0% 或达到某个成功率；
- Web Demo 使用完整 hybrid/reranker；
- 自动发现真实论文的人群、干预、终点和时间错配；
- 零幻觉、临床可靠、开放世界高召回或可用于治疗建议。

## 11. 停止条件

v0.4 在以下条件全部通过后发布并结束：Ruff、完整 tests、wheel 构建、release manifest、隐私扫描、Demo 的检索/筛选/导出、8 个 scope controls、README/案例/简历数字一致，以及 GitHub tag/Release。完成后不再增加模型、评测集、真人研究或云部署。

这让项目以一个诚实而完整的 PM 闭环结束：定义问题、构建 MVP、设计测量、发现测量失败、做出停止决策、把学习固化进产品，并准确限制最终主张。
